PulseWave AI Support

A customer support and RMA assistant for three products that answers only from their manuals, so customers get verifiable help instead of generic or invented steps.

About me

Hi, I am Sumit Patel, an embedded systems engineer moving into AI engineering. I build things that must work reliably on constrained hardware, and I brought that mindset here: small footprint, clear failure states, no guessing.

The problem

Support bots give generic answers, and plain LLMs invent features or unsafe troubleshooting steps.

The approach

Retrieve passages from the real manuals, answer only from them, and cite the source.

One knowledge base, three products

Airdopes Apex

Earbuds manual: pairing, touch controls, Beast Mode, care, reset and RMA.

Stone Spark

Speaker manual: TWS, AUX and microSD modes, IPX7 rules, reset and RMA.

StormCall Plus

Smartwatch manual: app binding, calling, health sensors, restart, reset and RMA.

All three manuals share the same seven-chapter structure. They are split into 88 chunks (27, 29 and 32 per manual) in one pgvector collection, and every chunk is tagged with its product so a search can be limited to one manual.

How a question becomes an answer

  1. 1. QuestionThe browser posts JSON and a session id to /chat. The server adds the last few messages of that session.
  2. 2. RouteLangGraph sends serial, order and ticket IDs, or "my warranty" questions, to the records. Everything else goes to the manuals.
  3. 3. RetrieveFastEmbed embeds the question locally. The pgvector search is limited to the product named in the chat or behind the serial number.
  4. 4. GuardThe prompt limits the model to the retrieved context and tells it to decline when the answer is missing. An optional distance threshold can also reject weak matches.
  5. 5. AnswerGemini Flash replies with sources. A backup model runs if it fails, then plain manual excerpts.

Warranty and return questions never reach the language model. Plain code reads the records, collects the serial number and order ID across messages, and opens a ticket only when both match and the warranty is active.

Measured on a hand-written set of 30 answerable and 8 out-of-scope questions across the three manuals (88 chunks). Retrieval is scored the way the app searches: limited to the product's manual, top 4 passages.

Engineering decisions

Grounded retrieval, not model memory

RAG over Supabase pgvector ties answers to the manufacturer manuals, and each reply lists the source it used.

Product-aware retrieval

Chunks carry a product tag, so asking about the Stone Spark cannot return passages from the Apex manual.

Deterministic warranty and returns

No model decides who gets a ticket. A return needs a matching serial number and order ID, and each device can have one open ticket.

Multi-turn sessions

The server keeps the last 8 messages per session for 30 minutes. They live in memory, so the demo runs on a single instance.

Graceful failure

HTTP 429, timeouts and offline servers get a clear message and a retry button. If the main model fails, a backup model answers, then manual excerpts.

Idempotent ingestion

Re-running ingestion replaces a manual's chunks instead of duplicating them, so repeats cannot crowd out relevant passages.

Free-tier protection

First questions are cached for an hour, each IP is limited to 12 questions a minute, and local embeddings cost nothing per query. The free Gemini key allows 20 model requests a day, after which the app shows manual excerpts.

Safe by default

Output is rendered as text, never HTML. Record tables use row level security and return no customer data.
